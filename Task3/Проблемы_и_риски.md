## Основные проблемы и риски

1. ### Монолитный core-app
   
Проблема:
- Основной бэкенд отвечает за всё: отображение данных, оформление заявок, работу с клиентами.

Риски:
- Перегрузка при росте нагрузки (особенно после запуска рекламы).
- Узкое горлышко всей архитектуры.
- Трудности масштабирования.
  
2. ### Синхронные запросы к ins-product-aggregator

Проблема:
- Каждый вызов инициирует цепочку запросов к страховым API.

Риски:
- Любая задержка/ошибка у страховой → сбой всей цепочки.
- Невозможность обрабатывать большое число запросов.

3. ### API партнёров без лимитов
Проблема:
- Один партнёр может генерировать до 250 RPS вместо допустимых 20 RPS.

Риски:
- Вызывается деградация производительности.
- Нарушаются SLA для других партнёров.

4. ### Отсутствие мониторинга и алертов
Проблема:
- Система не оповещает о сбоях самостоятельно.

Риски:
- Простои до устранения могут длиться часами.
- Финансовые потери и снижение доверия клиентов.

5. ### Единая PostgreSQL БД на одной ВМ

Проблема:
- Все данные хранятся на одной машине без резервирования.

Риски:
- Точка отказа.
- Невозможность масштабирования по мере роста нагрузки.


### Общие риски при росте нагрузки:
- Недостаточная масштабируемость.
- Уязвимость к пиковым нагрузкам.
- Потеря клиентов и партнёров.
- Финансовые убытки при простоях.
  
## Архитектурное решение

### Переход на EDA архитектуру

- В качестве брокера можно взять Apache Kafka.
- Вместо синхронных REST-запросов между сервисами используется публикация и подписка на события.

Примеры событий:

ProductInfoUpdated — публикуется ins-product-aggregator при получении новых тарифов.

PolicyIssued — публикуется core-app при оформлении новой страховки.

ClientUpdated — при изменении клиентских данных.


### Использование Transactional Outbox
Для публикации событий из core-app используется паттерн Transactional Outbox. Это исключает потерю сообщений и дублирование данных.

### Асинхронная синхронизация тарифов
ins-product-aggregator не отдаёт данные синхронно по REST, а отправляет события ProductInfoUpdated.
Сервисы core-app и ins-comp-settlement подписываются на эти события и актуализируют у себя тарифы.

### Ограничение нагрузки от партнёров
Каждому партнёру назначается индивидуальный лимит (например, 20 RPS). Превышения логируются, лишние запросы отклоняются.
